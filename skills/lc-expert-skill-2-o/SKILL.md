# 开源信用证审核

本 Skill 面向出口企业审核信用证草稿、SWIFT 报文和信用证项下交单文件。它区分三类依据：信用证原文、适用的 ICC 规则与银行实务、用户确认的企业政策。三者不得混写。

## 首次使用

先运行：

```bash
python3 scripts/profile_store.py show
```

如果尚无配置，读取 [企业配置字段](references/profile-schema.md)，只询问当前任务真正需要的字段。整理成 JSON 后，先向用户展示拟保存内容和脚本返回的保存路径；获得确认后再执行：

```bash
python3 scripts/profile_store.py save --input <企业配置.json> --confirm
```

用户可以跳过配置并仅完成当前审核。配置文件只保存企业级审证偏好，不保存客户名称、信用证号码、金额、完整单据、账号、密码或密钥。

## 审核模式

- **草稿审核**：判断条款是否可执行、是否可交单、是否存在收款或合规风险，并形成改证清单。
- **交单审核**：逐份核对信用证要求、单据内容和跨单据一致性，形成不符点清单。
- **专项复核**：只检查用户指定的条款、单据或风险；不得擅自扩大范围。

## 规则入口

审核前读取 [审核框架](references/review-framework.md)。

- 只有信用证明确表示适用 UCP 600 时，才将其作为约束依据。
- ISBP 用于理解 UCP 600 下的国际标准银行实务，不应写成修改了信用证或 UCP。
- 电子交单只有在信用证明确适用 eUCP 时才按 eUCP 处理。
- 制裁、反洗钱、出口管制、银行政策和国家风险具有时效性；涉及结论时查询当前官方来源，并标明核查日期和适用法域。
- 本 Skill 是业务风险辅助，不替代银行最终审单、律师意见或监管裁定。

## 执行流程

1. 确认是草稿审核、交单审核还是专项复核，并锁定文件范围。
2. 列出收到的信用证和单据；只有文件身份、版本或对应关系会改变结论时才追问。
3. 读取本机企业配置。配置与信用证冲突时，分别标注“信用证要求”和“企业政策”，不得把企业偏好冒充 ICC 规则。
4. 一次提取并记录信用证字段、子条款编号、单据页码和关键原文；无法读取的内容标记为“无法核实”。
5. 按审核框架检查条款可执行性、时间链、单据要求、运输、保险、费用、付款、软条款、制裁措辞和跨单据一致性。
6. 每个问题写明：位置、原文或事实、问题性质、判断依据、可能后果、建议动作。条款位置尽量精确到 `46A-3`、`47A-5` 等子项。
7. 高风险和无法核实项排在前面。没有证据时不得推断银行资信、制裁命中、客户动机或单据事实。
8. 按用户本次要求或企业配置生成报告。写入文件前确认目标路径；生成后回读或打开验证。

## 输出最低要求

- 审核对象、版本和日期清楚。
- 信用证原文、ICC规则、企业政策、经验建议和待核实项明确分开。
- 风险分为高、中、低，并给出可直接执行的改证或改单建议。
- 交单审核包含文件清单、存在性检查、逐份审核和跨单据核对。
- 不声称“银行一定接受”或“必然拒付”；最终接受性取决于信用证、适用规则、适用法律和相关银行。
